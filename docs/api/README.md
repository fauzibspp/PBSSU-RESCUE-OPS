# API contract conventions

PBSSU-API-001 v0.1. [openapi.json](openapi.json) is the OpenAPI 3.1.0 / API version 0.3.0 approved documentation baseline. JSON is chosen for dependency-free parsing; no backend exists. The document includes explicit DTOs, response schemas, security, operation IDs and traceability extensions. Formal validator/code-generator compatibility remains a future tooling gate.

Base path `/v1` is included in the placeholder server URL. `api.example.invalid` is documentation-only. Protected sessions use native Bearer or web access-cookie plus csrfHeader; credential-entry, action/challenge/handoff proof and refresh operations have explicit security overrides. Global identity/platform/proof operations do not take tenant selector headers; platform operations require a separate platform capability. TENANT operations alone require `X-Organization-Id`, resolved through current server-side membership. Tenant IDs never occur in request DTOs. Unknown fields are rejected. UUID paths are not authorization. GET responses use field whitelists and never serialize raw ORM rows.

All operation IDs are permission registry keys initially, grouped into approved roles during M01. Their presence is not an automatic grant. Responder reads/writes additionally require assignment. Sensitive-data/audit/export scopes require explicit grants. Platform organization onboarding is narrowly authorized and does not grant operational access. Identity lifecycle endpoints are defined as pending Q-03 policy candidates. Victim-data entry APIs and sensitive contacts are deliberately deferred until Q-09; schema reserves restricted storage and MVP report snapshots mark private sections as restricted/not recorded.

M00.2 candidate OpenAPI0.3.0 now aligns identity challenge/session metadata, MFA/proof/recovery/session commands and tenant invitations with the [40-entity schema](../architecture/DATABASE-SCHEMA.md). Exact permission keys are reconciled in the [authorization catalogue](../security/AUTHORIZATION-MODEL.md). createMembership is removed: inviteMember reserves intent; acceptInvitation reserves PENDING_ACTIVATION membership; activateInvitation alone grants roles after verified email/required MFA/current delegation. FIRST_ADMIN never grants operational roles. Q-01/Q-03 are APPROVED, Q-04 is APPROVED AS IMPLEMENTATION BASELINE; exact patches/digests/runtime results remain unverified.

Ordinary list responses have bounded items and opaque `next_cursor` (null at end); limit defaults 50/max 200. Sync pages use next_cursor/has_more and batches max 50 operations. Cursor tokens bind tenant/user/visibility scope. Report snapshots have explicit bounded arrays; agreed real-world limits must be verified during load/UAT. Optional fields are omitted, not null, unless schema explicitly permits null. Instants use UTC Z; UI converts MYT. GPS uses named longitude/latitude fields. All proposed numeric quotas await Q-04/Q-06 approval.

Guarded commands carry integer base_version. Mismatched versions return 409/current_version when permitted. Assignment updates guard incident.version; sync field operations also guard parent incident version. Lifecycle graph, report numbering and maker/checker rules come from SRS. Append-only evidence accepts a UUID; duplicate direct create with identical payload may return existing authorized record, but changed content must conflict. Mobile reliable replay uses sync operation IDs and canonical payload hashes; infrastructure/dependency retry does not finalize a receipt. Receipts never bypass current authorization.

Errors use code/message/correlation_id and optional current_version; no private payloads or existence leaks. A foreign-tenant resource is 404. Missing permission in current tenant is 403. Per-operation sync conflicts appear in the 200 results envelope; whole-request validation/authentication errors are HTTP errors. Expired pull cursor is 410, with safe resnapshot required. Rejected lifecycle commands are 422; races are 409. Rate limits return 429 and future implementation should include Retry-After.

Generic identity responses contain metadata/handles only; secret storage, audits/errors/logs never expose credentials. [C-02 handoff policy](../security/CREDENTIAL-HANDOFF.md) explicitly isolates sensitive release to redeemCredentialHandoff. Only its 200 application/vnd.pbssu.credential-material+json response may contain native-session tokens or pending TOTP/code material; only its WEB SESSION 204 branch issues Secure/HttpOnly session cookies and a bound CSRF cookie. There is no generic application/json material representation and no credential-value example. This is a documented authorized boundary under [owner approval](../planning/STAKEHOLDER-APPROVAL-2026-11-07.md), not a generic-response exception.

C-02 is RESOLVED_POLICY_CONTRACT; adapter readiness is a runtime implementation gate, and production email/secret delivery remains NOT AUTHORIZED. M01 must use synthetic example.invalid recipients and a controlled mock mail adapter without SMTP/provider credentials, real network sends or fallback. A private local test mailbox is available only to authorized testers; it is not a generic production API and never logs synthetic links.

Initial session metadata uses SESSION_HANDOFF_REQUIRED; it does not authenticate a client or assert delivered credentials. Binding/subject/purpose/original client/version/expiry/one-use checks and completed required password/MFA proof precede release. Native refresh uses X-Refresh-Token; web refresh uses __Host-pbssu_refresh; both return only handoff metadata before dedicated redemption. Cookie-authenticated mutations need Origin/CSRF checks; ordinary web access uses __Host-pbssu_access, native uses Bearer. Logout can use access or refresh solely to revoke, including after access expiry. Failure never returns cached raw material or waives MFA.

Login, invite acceptance, reauthentication and factor-replacement initiation send a client-generated >=256-bit writeOnly binding; its hash binds follow-up challenge requests through X-Auth-Challenge-Binding. Handle UUID alone is insufficient. Bound commands validate subject/purpose/expiry/authentication_version and consume once; MFA-to-invitation progression returns a new activation challenge. Anonymous security on proof entry means a validated proof workflow, never tenant authorization. Existing accounts accepting an invitation must also authenticate as its recipient; a supplied new_password cannot reset an existing account.

revokeSession accepts access OR refresh proof and only revokes the identified family even when access expired. refreshSession requires cookie/native-header refresh proof (no anonymous fallback), serializes consumption/successor creation and returns handoff metadata only. Session listing/revoke commands are own-subject only; challenge/self/global capabilities are not tenant-delegable permissions. Global identity audit is separate from tenant listAuditLogs. CSRF/Origin protections and secure native storage must be implemented and verified under the defined delivery policy.

Media follows reserve grant → private quarantine upload → complete → scan → READY → authorized download grant. Upload URL is never a public read URL. Proposed limit is 10 MiB JPEG/PNG and five-minute grant; provider/scan policy remains Q-04. Report export queues a job, then reauthorizes job reads and returns redacted text or brief private URL only for an approved snapshot. Export never delivers a message externally. Notification deliveries are internal only and have no public API in M00.

`x-requirements`, `x-modules`, `x-entities`, `x-tests` support the traceability matrix. NFR suites apply across operations in addition to per-feature tests. Read-only output schemas contain organization_id for context; request DTOs do not. [OpenAPI 3.1 specification](https://spec.openapis.org/oas/v3.1.1.html) defines the standard; M00 structural checks do not certify full standards conformance or runtime security.
