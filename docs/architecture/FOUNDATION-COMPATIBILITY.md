## ORM/query-builder alternatives

| Option | Assessment for this project |
| --- | --- |
| Kysely + pg (recommended) | Typed SQL with explicit transaction ownership; direct SQL migrations preserve tenant FKs, RLS policies, grants and geography without assuming ORM metadata encodes them. No built-in tenant security or auto-generated migrations; SQL review/type maintenance are project duties. |
| TypeORM 0.3 family | Candidate for entity-centric Nest integration; QueryRunner pins a connection and migrations support explicit SQL. A viable fallback, but RLS/grants/geospatial constraints still need authored SQL and runtime queries must always use the runner/transaction manager. Page extraction for current official migration guide was empty; exact current version/ranges are UNVERIFIED in this review. [Official migration guide](https://typeorm.io/docs/advanced-topics/migrations/) |
| Prisma 7 family | Official docs distinguish schema representation from underlying database support and allow custom migrations for unsupported features. RLS/geography and raw SQL need explicit preservation/review; do not label Prisma inherently unable to use RLS or composite FKs. Not selected because this design prioritizes SQL ownership and avoids a second source of schema truth. Version-specific coverage/performance not tested. [Database features](https://www.prisma.io/docs/orm/v7/reference/database-features), [unsupported features](https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/unsupported-database-features) |

The recommendation is an engineering inference, not a comparative benchmark. No ORM automatically enforces all authorization or tenant isolation.

## Mandatory database support assessment

| Concern | Documented support / proposed implementation rule | Required M01 verification |
| --- | --- | --- |
| Migrations | Kysely up/down functions and raw SQL can express CREATE EXTENSION, composite constraints, policies, ENABLE/FORCE RLS, grants, functions/triggers and indexes. Separate schema-owner/migrator credentials from runtime. | Fresh/upgrade migration, repeat-run bookkeeping, failure atomicity/concurrent runner lock, clean schema/RLS/grant inventory. Destructive down operations never run against production automatically. |
| PostgreSQL RLS | PostgreSQL18 supports USING/WITH CHECK; owner and BYPASSRLS/superuser exceptions require non-owner runtime and FORCE. Tenant policies plus separate object authorization remain mandatory. | SELECT/INSERT/UPDATE/DELETE under runtime; missing/malformed context fails closed; denied row mutations have no side effects; runtime cannot ALTER policies/SET ROLE into owner or TRUNCATE. |
| Composite FKs | PostgreSQL supports multicolumn FK to matching unique parent keys; express (organization_id,id) and incident-qualified references explicitly in SQL. | Foreign tenant and same-tenant wrong-incident links fail; unique/nullable behavior tested. Report-family invariants requiring cross-row logic use reviewed triggers, not an invalid cross-row CHECK. |
| Transaction context | Within one checked-out transaction use parameterized set_config('app.organization_id', resolved_uuid, true) and actor context. Policies use current_setting(...,true) with null/empty context denying rows. Kysely repositories must receive the transaction object explicitly. | Commit/rollback/timeout/cancellation and nested-call tests prove no session context leaks; root db/pool.query cannot be used from tenant repositories. |
| Connection pooling | Start with one bounded pg.Pool per process/credential boundary and transaction callbacks. Same connection for BEGIN, context and all queries; no network calls/scanning inside DB transaction. | Pool max=1 tenant alternation, mixed concurrent tenants, worker reuse, exceptions and failed rollbacks. Budget sum of pools across API/workers against DB connections; discard damaged connections. |
| External pooling | PgBouncer deferred. Transaction pooling requires transaction-local state and forbids assuming session state persists; statement pooling incompatible with this multi-statement protocol. | If later adopted, review mode, prepared statements/version and rerun all tenant-context tests. Direct approved migration connection, not runtime transaction-pool routing. |

Database capability sources: [PostgreSQL RLS](https://www.postgresql.org/docs/18/ddl-rowsecurity.html), [constraints](https://www.postgresql.org/docs/18/ddl-constraints.html), [transaction-local settings](https://www.postgresql.org/docs/18/functions-admin.html), [pg transactions](https://node-postgres.com/features/transactions), [pg pools](https://node-postgres.com/apis/pool), [Kysely transactions](https://kysely-org.github.io/kysely-apidoc/classes/Kysely.html#transaction), [PgBouncer modes](https://www.pgbouncer.org/features.html).

RLS is defense in depth against query omission, not a security boundary against a compromised backend that possesses its DB credentials and can set arbitrary tenant context. Parameterized queries, trusted tenant resolution, restricted credentials and SQL-injection prevention remain necessary. Referential-integrity checks can bypass row visibility; normalize constraint errors to avoid leaking foreign-resource existence. Distinct global identity/platform bootstrap service grants must not grant operational queries. Migration logs/diffs may contain structural names only, never private rows.

Transactions default to READ COMMITTED with explicit row locks/unique constraints for shared counters and approvals; choose stronger isolation only where demonstrated necessary and retry full transactions on approved transient failures. Kysely0.29.8 includes PostgreSQL failed-rollback/aborted-commit fixes; pinning older patches loses those fixes. Async context storage may carry request metadata for logging, but must not be the sole guarantee that a repository uses the checked-out transaction.

## Mobile encryption acceptance and fallback

Use versioned local migrations with transactions and foreign_keys enabled; do not copy sample downgrade-delete behavior. Partition per user/organization, random database key in OS secure storage, no password-derived key reuse, encrypted WAL/journal review, OS backup exclusion for secrets/caches, close handles before account switch/purge, no plaintext fallback if SQLCipher/key setup fails. Verify cipher_version, encrypted-file unreadability without key, restart/outbox persistence, migration from previous encrypted schema, wrong-key rejection and Android/iOS native loading. Key loss requires safe server resnapshot; warn that unsynced local evidence cannot be recovered without its key.

Do not claim plain sqflite, OS file protection alone or the sqlite3 Dart binding automatically encrypts data. Drift/sqlite3 plus a reviewed SQLCipher native build is an alternative only if the candidate fails, requiring a new compatibility/license decision. SQLCipher Community has source and redistribution terms; binary components/plugin/transitive licenses still require inventory review, not a legal-compliance assertion. [SQLCipher license](https://raw.githubusercontent.com/sqlcipher/sqlcipher/master/LICENSE.md). macOS/Xcode and real device access remain dependencies; no build was run.
