# Q-03: Local authentication and secure recovery

PBSSU-AUTHN-001 v0.3.0, 2026-11-07. Q-03 APPROVED by project owner; C-02 policy/contract resolved. [Approval evidence](../planning/STAKEHOLDER-APPROVAL-2026-11-07.md) is separate from runtime verification. No identity service/account exists yet.

## Credentials and enrollment

Use local verified email/password identities in the existing global users service. Email normalization has one documented application rule (trim and case-normalize consistently), with original address preserved for delivery. Verified email is identity evidence, never organization authorization. Invite-only onboarding for MVP: platform onboarding invites the first organization admin; tenant admins invite other members. Accepting an invite verifies the email, sets a password if needed, and creates/activates only the intended membership. An existing account must authenticate to accept; email matching alone must not attach a membership. Invitation acceptance and token consumption are atomic. Public organization creation, SSO and social sign-in remain outside MVP.

M00.2 replaces createMembership with inviteMember and aligns onboardOrganization to ONBOARDING/FIRST_ADMIN reservation. Intended grants live in invitation_roles; acceptance yields PENDING_ACTIVATION, and only activateInvitation after verified recipient/email/required MFA can install effective membership_roles. Existing-user UUID/email knowledge cannot create active access. A bound challenge is restricted global identity proof, never a tenant role. First-admin activation grants Organization Admin only; operational roles require separate reviewed delegation.

Use approved Argon2id with unique CSPRNG salt >=16 bytes and PHC-formatted hashes; initial proposed m=65536 KiB, t=3, p=1, benchmarked on deployment hardware before adoption. Never lower below the reviewed minimum without a recorded security decision; OWASP currently documents a 19 MiB/t=2/p=1 Argon2id baseline. Rehash on successful authentication after parameter upgrades. Bound hashing concurrency and throttle attempts to prevent memory exhaustion. Use a maintained Argon2 binding; exact package/build compatibility on Node 24/Windows/Linux remains unverified. No passwords, reset tokens or hashes in logs. [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

Proposed password policy: minimum 15 characters, support at least 128 characters and passphrases, no arbitrary composition rules or periodic forced changes; reject known-compromised/common passwords using an approved source without transmitting full passwords. Never silently truncate. Changes after suspected compromise revoke sessions. Existing M00 LoginInput length is a transport bound, not the final password-setting policy; creation/reset DTOs must express the approved limits. Rate-limit by account and source with generic errors and bounded backoff; avoid an attacker-controlled permanent account lock.

## MFA and assurance

Require MFA for platform admins, organization admins, control room operators, commanders, auditors and anyone with custom privileged grants (RBAC writes, control commands, report/audit/export or private-data access). A global user holding any such active grant must complete MFA for full sessions in every organization, preventing a low-privilege tenant login from bypassing the policy. Until enrolled, issue only short enrollment/verification challenges, not operational tokens. First-factor success never returns a full privileged session before MFA.

Use approved TOTP plus single-use recovery codes for MVP; optional WebAuthn security keys are a later enhancement, not a claimed phishing-resistant TOTP property. Encrypt TOTP seeds with a separate managed encryption key; never hash a seed that must be used to verify codes. Enrollment requires recent password verification, confirmation of a valid TOTP and a dedicated proof-bound one-time recovery-code handoff. Allow bounded clock skew (proposed +/- one 30-second step), persist the last accepted timestep and prevent replay. Challenges are single-use, server-bound to user/purpose, proposed five-minute expiry and maximum five attempts, then restart authentication. MFA failures use generic responses and redacted audit. [OWASP MFA guidance](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html)

Generate ten recovery codes of >=128 bits entropy each; release once through the dedicated proof-bound provisioning handoff and store only hashes. Redeeming one is atomic and counts as a recovery MFA event with notification and audit. Recent MFA (proposed five minutes) plus password confirmation is required to change email/password/MFA, delegate privileged roles or approve a report. Refreshing a session does not advance auth_time or mfa_verified_at. Privileged elevation requires verified enrollment and appropriate step-up before the new authority can be used.

## Sessions, rotation and clients

Access JWTs: proposed five-minute lifetime, asymmetric signing/key rotation, fixed algorithm/issuer/audience, sub/sid/jti/iat/exp/auth_time and MFA assurance claims. Authorization uses current server-side memberships/roles, not embedded role claims. Every protected request checks session/user status and required assurance; revoked sessions fail despite unexpired JWT. Signing/private and TOTP encryption keys have different custody and rotation procedures.

Refresh tokens: opaque >=256-bit random secrets; store only a digest, token family, session ID, issued/expiry/consumed/revoked times. Each use atomically consumes the old row and issues one successor. Reuse revokes the entire family/session, audits and notifies the owner. Serialize refreshes on clients; an ambiguous network failure requires sign-in rather than allowing replay. No permissive replay grace period. Retain consumed digests through the family lifetime to detect older-token reuse. This borrows token-rotation controls from [RFC 9700 section 4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14); the MVP is a first-party local session service, not a claim of implementing an OAuth authorization server.

| Session class | Proposed refresh idle limit | Absolute family lifetime |
| --- | --- | --- |
| Web ordinary | 12 hours | 7 days |
| Mobile ordinary | 7 days | 30 days |
| Any privileged session | 8 hours | 24 hours |

Rotation cannot extend absolute family lifetime. These durations are recommendations for approval, not an offline data-retention policy. Offline field entry may continue under approved local-unlock/cache limits, but synchronization always needs a live authorized online session. Q-05 governs device exposure and replay horizons separately.

## C-02 approved delivery boundary

The [one-time handoff policy](CREDENTIAL-HANDOFF.md) supersedes M00.2's intentionally unresolved delivery restriction. Generic login/refresh/MFA/invitation/recovery APIs remain metadata-only and never return secret material. Only redeemCredentialHandoff, explicitly declared in OpenAPI0.3.0, can release purpose-bound material after completed required proof. This is a documented narrow channel authorized by the owner, not an undocumented generic-response exception.

Web SESSION handoff uses Secure/HttpOnly host-only cookies plus bound CSRF controls; native SESSION handoff and TOTP/recovery provisioning use only application/vnd.pbssu.credential-material+json on that route. Handoff IDs are not proof. Bind to current user, exact purpose, original client kind, authentication_version and prior completed first-factor/required MFA; release once under lock, purge encrypted material, no logging/auditing/caching of bodies/headers/secrets. A lost response requires a fresh authorized workflow, never raw response replay. SESSION handoff TTL is 60 seconds; TOTP/code release TTL five minutes. Recovery-code/factor lifetime is separate.

M01 uses synthetic identities/material and a controlled mock mail adapter with no actual outbound messages. Authorized local testers may read synthetic test links in a private mock mailbox, not logs/public APIs. Email is an invitation/account-proof channel, not a source of MFA seed/recovery-code authority. Real provider/sender selection, key custody, safe production delivery and all-factor recovery owners remain separately gated. No real user or production secret delivery is authorized.

A client generates a CSPRNG >=256-bit binding nonce and sends it with login/accepted invitation/reauthentication or factor-replacement initiation. Server stores only its digest. Restricted follow-up requests require that nonce in X-Auth-Challenge-Binding and a challenge UUID; neither UUID alone nor arbitrary caller user/tenant IDs suffice. Purpose/subject/authentication_version/expiry/attempt counters are checked under lock. Returning a challenge handle is not returning a secret credential. MFA completion tied to a pending invitation consumes its challenge and returns a fresh activation challenge; successful explicit activation still requires a completed authenticated session handoff, with no implicit operational role from the handoff itself. Normal step-up updates only the bound existing session and never advances assurance on refresh.

Cookie-authenticated request paths require the explicit X-CSRF-Token security scheme plus trusted-Origin checks; native storage/transport requires device validation. Never put session/refresh credentials in logs, localStorage, URLs or ordinary SQLite. Only the approved one-time invitation/account-proof email may use a fixed trusted fragment capture, then a writeOnly POST body; no token-bearing generic response/redirect or actual credential example. No real delivery is performed.

Logout revokes the current family and clears cookie; logout-all/password reset/account disable revoke all sessions. Membership removal revokes that tenant authorization immediately without needing to disable unrelated memberships. Email/MFA changes revoke other sessions, with policy-driven fresh session issuance after reauthentication. The aligned revokeSession accepts access OR refresh proof even when access expired; it revokes rather than rotates the family, and listSessions/revokeOwnedSession/revokeAllSessions are own-user only.

## Account recovery

Password-reset request always returns the same generic response whether an email exists. Use >=256-bit opaque one-time token, hash at rest, purpose/user-bound, proposed 15-minute expiry, rate limits and out-of-band email through an approved sender. Build recovery URLs from fixed configured origin, never Host headers. Use approved out-of-band proof presentation and submit it in the reset confirmation POST body; never echo it through API redirects or URLs. UI must suppress third-party content/referrers and clear any external delivery-link fragment after capture; avoid request-body/query logging. Validate/consume token atomically with password replacement, invalidate sibling reset tokens and all sessions; notify account owner. Do not automatically sign in after reset. [OWASP account recovery](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)

Email password reset does not remove MFA or satisfy privileged session assurance. Normal factor change requires current password and existing factor. One recovery code can replace a lost authenticator after reauthentication. Loss of both authenticator and codes requires an audited manual identity process with two independent approved recovery custodians; email possession or a platform/tenant admin request alone cannot disable MFA. Proposed 24-hour notification/cooling period for manual factor reset, invalidate all prior credentials/recovery codes/sessions, require re-enrollment. If custodians/evidence criteria are not approved, this manual path stays unavailable; no support bypass. The final custodians, evidence standard, mail sender and time limits remain explicit approval/operational gates.

## Pending delivery and refresh details

An initial session is PENDING_DELIVERY and authorizes no ordinary API until its SESSION handoff is redeemed after all required authentication/MFA. Generic Session.authentication_state is SESSION_HANDOFF_REQUIRED, not a claim of delivered credentials. A rotated native refresh value uses the same dedicated handoff, not generic refresh JSON; web uses its secure cookie only at redemption. Persist the binding separately in native OS secure storage, never logs/SQLite. Failed/expired handoff revokes an unactivated session and undelivered successor; reauthenticate. Existing active access may expire normally, but no refresh replay grace is introduced.
