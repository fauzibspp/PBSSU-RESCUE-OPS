# C-02: Approved invitation and credential provisioning handoff

PBSSU-HANDOFF-001 v0.3.0, 2026-11-07. Policy authority: [project-owner approval](../planning/STAKEHOLDER-APPROVAL-2026-11-07.md). C-02 is RESOLVED at policy/contract level. Adapter implementation, operational acceptance and production-provider authorization are separate gates. No handoff, mailbox, account or secret exists merely because this document defines one.

## Invitation channel and M01 restrictions

onboardOrganization/inviteMember create only pending intent and a purpose-bound >=256-bit invitation proof. Store its digest, intended recipient/tenant/roles, expiry and an encrypted short-lived mock-delivery envelope; never return the proof from generic onboarding/invitation APIs. Use a fixed trusted invitation origin and fragment proof (not server-query/path tokens) or manual code capture, followed by a TLS POST acceptInvitation. Email possession alone does not authorize an existing account: authenticate that recipient; new identities must set a password and complete required MFA before explicit activation. Invitation expiry/revocation, authentication_version, recipient/delegation and tenant composite-FK checks remain mandatory.

M01 delivery is a controlled mock adapter: synthetic addresses under example.invalid, no SMTP/API/provider credentials, no network send fallback, no real recipient input. Invitation lifetime is at most 24 hours; shorter expiry/revocation always wins. Startup/config validation must deny real delivery mode and real recipient addresses in M01. A private bounded in-memory or equivalently protected local mock mailbox may expose synthetic invitation/reset links to authorized local testers; never console/application logs, generic API responses, source control, public ports or operational audit payloads. Tests use legitimate proof paths rather than fabricated verified sessions. This document creates no mailbox listener or implementation.

Future real invitation delivery requires a separately approved provider/sender/domain, ownership, transport/authentication, retention/key custody and explicit production authorization. Neither this baseline nor selecting an email adapter permits real messages.

## Explicit dedicated material release

Generic login/MFA/refresh/recovery endpoints return only challenge/session/delivery metadata and non-authorizing handoff UUIDs. The sole material-release endpoint is POST /auth/credential-handoffs/{handoffId}/redeem (redeemCredentialHandoff). It is intentionally separate from ordinary application/json responses. Its explicit authority is C-02; this is a documented narrowly scoped contract, not renamed/encoded secrets hidden in a generic DTO.

The server creates a credential_handoffs record bound to one user, purpose, original client kind, authentication_version and completed proof/session/enrollment. Store only the client-binding digest and encrypted expiring material, not raw secrets in logs or ordinary outbox/audit rows. The client must supply the original CSPRNG >=256-bit binding in X-Auth-Challenge-Binding; UUID/purpose selection alone cannot authenticate it. Do not log header, cookies, body, URI material, encrypted envelope or decrypted material. Server-chosen purpose/client mode cannot be changed by the redemption request.

| Purpose | Prior proof required | Dedicated output and lifetime |
| --- | --- | --- |
| SESSION | Completed password and required current MFA, or valid atomic refresh rotation; verified subject/session/version and client binding. Pending invitation MFA cannot mint an operational session. | One-time handoff expires after 60 seconds. Web: 204 with Secure/HttpOnly host-only access/refresh cookies and bound CSRF cookie. Native: 200 application/vnd.pbssu.credential-material+json with access/refresh values for this subject/session only. |
| TOTP_SETUP | Verified recipient/email and recent password challenge; replacement additionally requires existing MFA or a valid recovery-code step-up. Existing active MFA can never be replaced through password/email reset alone. | One-time handoff expires after five minutes; dedicated custom-media payload includes only the bound pending enrollment seed/otpauth material. No seed sent by email or generic API. No operational access before successful TOTP confirmation and activation. |
| RECOVERY_CODES | Newly confirmed TOTP enrollment/replacement or recent password plus required current MFA/recovery-code assurance for rotation. | One-time handoff expires after five minutes; custom-media payload exposes one newly generated ten-code set once. Database keeps code hashes; release does not mark codes as used. Undelivered/expired sets must be invalidated and regenerated under fresh required proof. |

The delivery expiry bounds exposure of a handoff, not the lifetime of an already confirmed TOTP secret or unused recovery code; those follow factor/recovery policy. No signing/private keys, password hashes or database encryption keys are ever releasable through this route.

Redemption locks the handoff and verifies subject/purpose/client binding/version/expiry/state plus current user/session/MFA/invitation state. Atomically consume once, activate an initial PENDING_DELIVERY session where applicable and append only a redacted metadata event. Decrypt strictly for that response, erase the encrypted envelope and never cache/replay the sensitive response. Repeated/wrong-purpose/wrong-client/expired/revoked requests fail without material. A lost response requires a fresh authorized authentication/provisioning workflow; do not add an idempotent raw-secret response cache. Refresh serializes one successor, preserves absolute expiry and revokes ancestors on replay; a failed handoff never creates a refresh-replay grace period.

## Web/native transport controls

Web session redemption emits separate Set-Cookie headers, never a comma-joined credential list. __Host-pbssu_access, __Host-pbssu_refresh and __Host-pbssu_binding are Secure; HttpOnly; SameSite=Strict; Path=/; no Domain. __Host-pbssu_csrf is Secure/SameSite=Strict/Path=/ and client-readable for an explicit X-CSRF-Token echo validated against server-bound session state. All cookie-authenticated mutations (including refresh/logout) require trusted Origin, anti-CSRF validation and strict non-wildcard credentialed CORS. Generic response bodies and application JS never receive web access/refresh values. Clearing cookies during logout is not credential issuance.

Native sessions use the dedicated material media type only, access token in memory and refresh value plus client binding in OS secure storage. Native refresh uses redacted X-Refresh-Token; web refresh uses only its cookie. Server selects client mode from the completed proof, not request-controlled downgrade flags. Mobile/native transport/storage remains a future device-test gate, not proof supplied here.

Every sensitive redemption response uses Cache-Control:no-store, Pragma:no-cache, TLS, nosniff, no cross-origin exposure or redirects, and response/body/header capture disabled in reverse proxy/APM/debug tooling. MFA material is rendered only within authenticated provisioning context with no third-party scripts, analytics or persistence. Native/body and web/cookie branches cannot both issue credentials for one handoff.

## Recovery and separation of duties

Invitation/reset email is not an MFA recovery credential. Password recovery revokes sessions but keeps active MFA, code hashes and required assurance. TOTP replacement requires existing factor or recovery-code proof; loss of all factors/codes remains denied until the documented dual-custodian recovery procedure/evidence standard is operationally approved. Platform/tenant admins cannot waive those proofs. Real MFA seed/recovery-code delivery remains unauthorized until production security/operations review; M01 uses synthetic material through the same controlled handoff, not outbound mail.

## Evidence gates and references

T-026 covers one-time/purpose/client/subject/version/expiry, no premature SESSION handoff, first-admin activation, wrong-client concurrency, no replay/cache/log leakage, correct custom-media/cookie branches, mock-only recipient/sender restrictions and password-reset/MFA separation. These are future runtime tests, not executed here. Adapter absence/failure must fail closed without forged sent/received/acknowledged events.

Design references: [OWASP session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [OWASP MFA](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html), [RFC9700 rotation guidance](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14). These inform controls; the dedicated first-party contract is not a claim of OAuth-server compliance.

Web binding persistence: initial login/enrollment uses the in-memory client binding header. Successful WEB SESSION redemption also sets __Host-pbssu_binding HttpOnly so later refresh/handoff can retain the server-bound identity across page reload without putting proof secrets in localStorage. The handoff accepts that cookie only for the recorded web session, with Origin/CSRF checks and completed proof; it never replaces the original first-factor/MFA challenge. Native mode always uses the secure-store binding header, never a web-cookie downgrade. Logout clears access/refresh/binding/CSRF cookies. OpenAPI explicitly requires csrfHeader together with accessCookie, refreshCookie or handoffBindingCookie on cookie-authenticated reads and writes, not merely a descriptive note. Browser/multi-tab, expiration and storage behavior must be tested during implementation.
